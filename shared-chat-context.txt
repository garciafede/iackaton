### 1. No haría que ChatGPT “busque precios”

Éste para mí es uno de los puntos técnicos más importantes del proyecto.

El LLM debería entender:

- qué producto quiere;
- qué presentación;
- qué ubicación tiene;
- qué restricciones puso;
- qué quiere priorizar: cercanía/precio/disponibilidad.

Pero **no debería inventar ni recordar precios**.

El modelo debería llamar herramientas tuyas, por ejemplo:

```text
buscarProducto("coca cola zero 1.5l")

obtenerOfertas(
   productoId,
   latitud,
   longitud
)

buscarLocalesCercanos(
   latitud,
   longitud
)

obtenerPrecio(
   productoId,
   comercioId
)
```

La API actual de OpenAI permite justamente que un modelo utilice funciones/herramientas definidas por tu aplicación con argumentos estructurados. citeturn128711search0turn128711search1

Eso permite una arquitectura mucho más seria:

**LLM = cerebro/orquestador**  
**APIs/DB/RPA = fuente de verdad**

# 2. El verdadero desafío: ¿de dónde sacás los precios?

Probablemente ésta sea **la parte que determine si ganás o no**.

Google Maps puede decirte:

> Hay un Carrefour a 800 metros.

Pero Google Maps **no sabe necesariamente si ese Carrefour tiene Coca-Cola Zero 1,5 L ni cuánto cuesta**.

Por eso haría una capa denominada algo como:

### Product Intelligence Service

Con varias fuentes:

```text
                    ┌─ API comercio A
                    │
Producto ───────────┼─ Ecommerce comercio B
                    │
                    ├─ Scraper Playwright comercio C
                    │
                    └─ Catálogo/CSV comercio D
```

El sistema transforma todo a un formato común:

```json
{
  "product": "Coca-Cola Zero",
  "ean": "7790895001234",
  "size": "1.5 L",
  "store": "Carrefour",
  "branch": "Yerba Buena",
  "price": 2350,
  "currency": "ARS",
  "stock": true,
  "source": "...",
  "updatedAt": "2026-09-12T16:42"
}
```

Así podés mezclar distintas fuentes.

### Para la PoC

No intentaría resolver:

> Todos los supermercados de Argentina.

Resolvería muy bien:

**5-10 productos + 2-4 cadenas/comercios + una zona geográfica.**

Después en la presentación explicás cómo escalarlo.

Eso cumple perfectamente con la idea de una **PoC acotada, medible y orientada a resultados** que pide el reglamento. fileciteturn0file0L6-L10

# 3. Playwright/RPA puede ser una de las claves

Acá podés hacer algo bastante interesante.

Supongamos que:

```text
Carrefour
Vea
Jumbo
Farmacity
```

tienen ecommerce.

Un worker podría hacer:

```text
buscar "Coca Cola Zero 1.5L"

↓
abrir resultados

↓
identificar producto

↓
extraer:
precio
stock
promoción
sucursal

↓
guardar en PostgreSQL
```

Con:

**Playwright + Node.js + TypeScript**

No necesariamente haría el scraping cada vez que alguien escribe por WhatsApp.

Eso podría tardar 10-30 segundos.

Mejor:

```text
                 cada X horas
Webs ──Playwright─────────────→ PostgreSQL
                                    ↑
                                    │
WhatsApp → Agente IA ───────────────┘
```

Entonces la respuesta es prácticamente inmediata.

Además guardaría:

```text
price
last_checked_at
source
availability
```

Y respondería:

> $2.350  
> Última actualización: hace 37 minutos.

Eso aumenta muchísimo la **confianza y calidad de evidencia** de la solución.

Entonces podrías consultar:

```sql
PRODUCTO
+
```

Eso ya empieza a sentirse realmente como un **agente**, en vez de un simple chatbot.

# 5. Matching inteligente de productos

Los usuarios jamás van a escribir el nombre perfecto.

Van a poner:

```text
coca zero
coca sin azúcar
cocacola zero grande
coca 1 litro y medio
coca negra sin azucar
```

Pero tu base puede tener:

```text
Coca-Cola Sin Azúcar 1,5 L
SKU 12345
EAN 779...
```

Ahí la IA puede convertir:

```text
"coca zero grande"
```

en:

```json
{
  "brand": "Coca-Cola",
  "variant": "Sin Azúcar",
  "size": "1.5L"
}
```

Y después buscar en catálogo.

Yo empezaría con:

- aliases;
- fuzzy matching;
- SQL;
- LLM.

Y agregaría **embeddings/pgvector** solamente si realmente aportan algo.

No pondría una vector DB por poner “IA”.

# 8. Tecnología concreta que elegiría

Para una PoC de hackatón, mi stack sería:

**Frontend:** ninguno. WhatsApp es la UI.

**WhatsApp:** Meta WhatsApp Cloud API.

**Backend:** Node.js + TypeScript + Fastify.

**Agente:** OpenAI Responses API + Function Calling.

**Productos:** PostgreSQL.

**Geoespacial:** PostgreSQL + PostGIS.

**Matching:** LLM + fuzzy search; pgvector opcional.

**Ubicaciones:** Google Places API.

**Precios:** APIs de comercios cuando existan + Playwright cuando no existan.

**Jobs de actualización:** BullMQ / cron.

**Cache:** Redis si hace falta.

**Deploy:** Google Cloud Run. Para ir aún más rápido, Railway/Render.

**Observabilidad IA:** Langfuse.

**Testing:** Vitest + Playwright + Postman/API tests.
